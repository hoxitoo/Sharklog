# SharkLog — Контекст проекта

Bet tracker app — мобильное (React Native + Expo) и десктопное (Tauri v2 + React) приложение для учёта ставок. Первый релиз — RuStore: Free + «Pro навсегда» за 399 ₽ разовым платежом через Робокассу (продавец — ИП на НПД). Подписки 199 ₽/мес и 990 ₽/год через RevenueCat — для Google Play позже.

## Структура монорепо

```
apps/mobile/     — React Native 0.85 + Expo 56 (iOS + Android)
apps/desktop/    — Tauri v2 + React + Vite (Win / Mac / Linux)
packages/core/   — Чистая TS бизнес-логика (типы, статистика, Kelly, форматтеры, билдер стратегий)
docs/            — ROADMAP.md, ANALYSIS.md, PRIVACY_POLICY.md, RELEASE_GUIDE.md, RUSTORE_LISTING.md (тексты карточки RuStore),
                   legal/ (разбор возвратов, черновик оферты, тексты экрана покупки)
```

## Ключевые соглашения

- Деньги — **копейки (integer)**. `1000 ₽ = 100_000`. `formatMoney()` для вывода, `parseMoneyInput()` для ввода.
- `formatMoney(kopecks, currency='₽', maxDecimals=2)` — третий аргумент управляет знаками после запятой.
- На мобилке использовать `useFormatMoney()` (из `utils/useFormatMoney.ts`) вместо прямого `formatMoney` — он учитывает `settings.roundAmounts`. Ссылка стабильна (`useCallback` по `roundAmounts`), поэтому её МОЖНО и НУЖНО класть в зависимости `useMemo`/`useCallback`: мемоизированный заголовок секции без неё замерзал на той настройке, с которой смонтировался.
- Ставки — **UUID v4** (не timestamp). На мобилке — `uuid()` с fallback на Math.random (crypto может быть unavailable на Hermes/Android).
- PRO-функции мобилки — `<ProGate feature="...">` компонент.
- `packages/core` — без зависимостей на React/RN/Browser.
- `exactOptionalPropertyTypes: true` — нельзя писать `prop={undefined}`, нужен spread `{...(x ? { prop: x } : {})}`.
- **refund ≠ cashout**: `refund` = букмекер вернул ставку (отмена матча); `cashout` = игрок сам выкупил досрочно. Это два разных `BetStatus`.
- **formatPercent()** уже добавляет `+` для положительных значений — не добавляй префикс вручную.
- **`parseMoneyInput`** сохраняет ведущий `-` и парсит много-групповые разделители (`1 000 000`, `1.000.000`). Отрицательные значения отбрасывай на уровне формы (`stake > 0`), а не в парсере.
- **Запись в стор сериализована** через `writeChain` (промис-цепочка) в обоих `betsStore` — не вызывай `saveData`/`setItem` напрямую в обход `persist()`.
- **Пути в обход `addBet` не ставят напоминания** (импорт CSV/JSON, восстановление бэкапа) — после них дёргай `syncBetResultReminders`. Выключение тумблера должно снимать уже поставленные (`cancelAllBetResultReminders`), а не только прекращать новые.
- **`clearAll`** чистит только данные (ставки/дневник/банк), но СОХРАНЯЕТ настройки и подписку (PRO/язык/букмекеры) — не сбрасывай `settings` к дефолтам.
- **Даты-строки `YYYY-MM-DD`** парсь как локальные (`new Date(\`${d}T00:00:00\`)`), bare-строка парсится как UTC и смещает день. На десктопе локаль для `toLocaleDateString` — через `dateLocale(lang)` из `i18n`.
- **Очистка опциональных полей на edit**: `updateBet` делает merge `{...bet, ...updates}`, поэтому пустое поле, просто *опущенное* из `updates`, НЕ стирает старое значение. Чтобы очистить (напр. `closingOdds`/`cashoutAmount`), передавай ключ явно как `undefined` (через `... as Partial<Bet>`), а не опускай его.
- **gifted-charts: `hideDataPoints` убивает `customDataPoint`** — маркеры на линии не отрисуются. Для линий с метками (депозиты/выводы) рисуй свой SVG (`components/BalanceChart.tsx`), а не борись с библиотекой.
- **Логотип**: `assets/icon.png` — НЕПРОЗРАЧНЫЙ тайл (тёмный фон + белый знак) только для лаунчера/сплэша; внутри приложения показывай `assets/adaptive-icon.png` (прозрачный белый знак), иначе на экране виден тёмный квадрат. Рядом со словом «SharkLog» (шапка бокового меню) — `assets/logo-mark.png`, тот же знак, обрезанный по краям (176×120): у `adaptive-icon.png` поля безопасной зоны Android, и в прежнем квадрате 36 pt сам знак был 18×12 — мельче слова рядом. Десктоп: `public/logo.png` — прозрачный знак для тёмного UI, `public/logo-512.png` — оригинальный лок-ап на белом для README/лендинга.
- **Значки меню, видов спорта и дисциплин — авторский SVG-набор**, не эмодзи и не Ionicons: `<AppIcon name=… size={GLYPH.*} />` (`components/icons`). Исходник — `docs/design/icons/adaptive/*.svg` (48×48, цвета — CSS-переменные `--sl-icon-body/accent/support`); `node docs/design/icons/build-glyphs.cjs` превращает их в `glyphs.ts`, руками его не правь. Переменные react-native-svg не читает, поэтому у каждой фигуры не цвет, а РОЛЬ: `body` → `textSecondary` (или `color`), `accent` → `purpleText`, `support` → `raspberry` — разрешаются при отрисовке из живого `colors`, один набор на четыре темы. Активное состояние по правилу набора: `color={colors.purpleText}` — весь значок цвета акцента, как подпись. Спорт/дисциплина → значок только через `sportGlyph()`/`disciplineGlyph()` (`glyphNames.ts`, чистый модуль — jest не грузит TSX из тестов); неизвестное значение получает «другое». Новый вид спорта в core без значка роняет `__tests__/glyphs.test.ts`.
- **Значок уведомлений Android — `assets/notification-icon.png`** (белый знак на прозрачном, 96 px): Android берёт у него только альфа-канал, и непрозрачный `icon.png` в статус-баре был бы белым квадратом.
- **Версия приложения — `APP_VERSION` из `utils/appVersion`**, читается из `app.json` (с которого собирает EAS). Раньше её дважды набирали руками ('1.0.0' в Настройках и в аналитике), и поднятая только в `app.json` версия показывала бы старую и сама себе писала «есть обновление».
- **Палитра графиков — одна на всё приложение**: `theme/chartColors.ts` (`SERIES`: win/loss/pnl/balance/deposit/withdrawal). Не заводи цвета серий по месту.
- **Ландшафтный режим через rotate-трансформ** (`ExpandedDashboard`): экран поворачивается на 90° по часовой, поэтому отступы безопасной зоны надо ПЕРЕСТАВЛЯТЬ — `paddingRight ← insets.bottom` (там наэкранные кнопки), `paddingLeft ← insets.top`. Иначе контент лезет под системную навигацию.
- **Действия из уведомления применяй ТОЛЬКО после `isLoaded`** — на холодном старте стор ещё пуст, и `updateBet` по пустому массиву затем запишет пустой снапшот поверх реальных данных. В `App.tsx` действие буферизуется в ref и применяется в эффекте по `isLoaded`.
- **Уведомления: детерминированный id `bet-result-<betId>`** — планирование идемпотентно (повторное перезаписывает, а не дублирует), отмена O(1). Все записи сериализованы через `notifChain`, иначе отмена может обогнать планирование и напоминание запишется ПОСЛЕ закрытия ставки.
- **НИКОГДА `toISOString().split('T')[0]` для «дня»** — это UTC-день. В 00:00 по локальному времени восточнее UTC он даёт ВЧЕРА: ставка сохранялась прошлым числом, «Сегодня» в списке указывало на вчерашний день, дневник писался не в тот день. Единственный способ получить календарный день — `toYmd(date)` из core (и мобилка, и десктоп).
- **Даты только через `toYmd()`** — `toISOString().split('T')[0]` даёт UTC-день. Из-за этого ставка могла записаться завтрашним числом (и выпасть из статистики), а транзакции банкролла — попасть в другой день, чем текущий банк в шапке.
- **Напоминание о результате не должно приходить по закрытой ставке** — защита в три слоя: (1) `updateBet` снимает запланированное и убирает уже доставленное из шторки, (2) `syncBetResultReminders(bets, enabled)` сверяет расписание с реальностью при запуске и каждом возврате в приложение (отмена — fire-and-forget, её может «потерять» при убийстве процесса; импорт CSV тоже создаёт дрейф), (3) `setNotificationHandler` глушит показ в foreground через `setBetPendingResolver`.
- **Текст уведомления «запекается» в момент планирования, кнопки — в момент регистрации категории.** ОС хранит строку, а не ключ перевода, поэтому смена языка сама по себе не меняет ни запланированных напоминаний, ни кнопок «Выиграла / Проиграла». В `App.tsx` языковой эффект объявлен ПЕРЕД остальными эффектами уведомлений (React выполняет эффекты одного коммита в порядке объявления): сначала `applyLanguage`, потом `registerBetResultCategory` и `syncBetResultReminders(..., { rearm: true })` — перевыпуск ВСЕГО запланированного, и при смене языка, и при каждом запуске (так лечатся напоминания, запланированные старой сборкой по-русски). **`rearm` НЕ отменяет**: планирование под тем же детерминированным id само заменяет напоминание, а «отменить и перепланировать» теряло каждое, которому до срабатывания меньше минуты (такие уже не планируются) — то есть открыть приложение перед концом матча значило съесть его напоминание. Лимит в 50 слотов делят только ставки, чьё напоминание ещё впереди (`reminderFireAt`), иначе хвост старых незакрытых ставок вытесняет будущие матчи. Всё это — `__tests__/reminderSync.test.ts` с планировщиком в памяти; настоящий модуль импортируется по пути `../../src/utils/notifications`, потому что `../utils/notifications` jest подменяет моком. Раньше язык применялся ПОСЛЕ планирования, и англоязычный пользователь получал русские уведомления. `changeLanguage` здесь синхронный — ресурсы вшиты в бандл, бэкенда нет; добавишь загрузку переводов по сети — этот порядок сломается.
- **Час ежедневного напоминания — только `effectiveReminderHour(settings)`** (betsStore): у Free час фиксированный, у Pro свой. Бывший Pro хранит свой старый час, и чтение `settings.reminderHour` напрямую давало «20:00» на экране и уведомление в 09:00. Перепланирование — отдельный эффект в `App.tsx` по `[язык, эффективный час]`, он же срабатывает, когда проверка подписки при запуске снимает Pro.
- **`canAddBet() === false` — это две разные стены**: у Free кончились 50 ставок, или Pro упёрся в СВОЙ дневной лимит. Сообщение различай по `isPro` — одно на оба случая предлагало платящему пользователю «перейти на Pro».
- **Даты — `toLocaleDateString(dateLocale())`** из `i18n`, а не `language === 'en' ? 'en-US' : 'ru-RU'`: так казахский и белорусский экраны печатали русские месяцы.
- **Новую функцию в `utils/notifications.ts` добавляй и в мок** `src/__tests__/__mocks__/notifications.ts`, иначе падают тесты стора.
- **Банк считай только через core**: `currentBank(transactions, bets)` = `bankCash(transactions) + P&L`. Не пиши руками `deposit ? + : -` — транзакций ТРИ типа, и третий (`adjustment`) хранит знак В САМОЙ СУММЕ, а не в типе. Инлайн-редьюс молча его потеряет.
- **Банк в приложении ≠ баланс у букмекера**: букмекер списывает ставку сразу при постановке, приложение — только при расчёте. Поэтому `балансУБукмекера = currentBank − pendingExposure(bets)`. Это первое, что надо исключить при расхождении.
- **`adjustment`** — сверка с реальным балансом бука без фейкового депозита/вывода. Пользователь вводит реальный баланс, приложение само считает разницу и пишет её со знаком. Разницу считай от `currentBank − pendingExposure`, а НЕ от голого банка: у бука открытые ставки уже списаны, и сверка от банка запишет их как недостачу, которая не рассосётся после расчёта ставок. В `calcDailyBreakdown` у неё свой бакет `adjustments` — она двигает `balance`, но НЕ попадает во «Внесено/Выведено» и не рисует маркер депозита на графике.
- **CSV — один модуль на оба приложения**: `packages/core/utils/betsCsv` (`buildBetsCSV` / `importBetsFromCSV` / `importBetsFromRows`). Не заводи парсер или писатель по месту: раньше их было два, они разъехались, и выгрузка с телефона не открывалась на ПК.
- **Общий кэф экспресса — `combineExpressOdds()`**, округление до 2 знаков. Букмекер показывает и рассчитывает экспресс по округлённому коэффициенту (1.23 × 1.90 = 2.337 → платит по 2.34). Хранение сырого произведения давало «× 2.34» на экране и выплату по 2.337 — расхождение с реальным балансом росло с каждым экспрессом.
- **P&L одной ставки — только `betPnl()`**. Ручные `status === 'won' ? ... : ...` уже приводили к тому, что выкуп экспортировался нулём, а проигранный фрибет — полной потерей.
- **Кумулятивные кривые сортируй по `date + time`, не по `createdAt`** — ставка, занесённая задним числом, иначе прыгает в конец графика и расходится со списком ставок.
- **Процент на карточке ставки («+3.2% банка») — от банка НА НАЧАЛО дня ставки, не от текущего.** От текущего каждая старая карточка меняла бы число при любом депозите, а серия побед уменьшала бы проценты тех самых ставок, что её сделали. Банк берётся из `bankAtBetTime` — той же функции, что у `calcPlanCompliance`, поэтому «банк» у плана и у карточки один. Процента нет у фрибета (не свои деньги), возврата и ожидающей, когда банк не ведётся вовсе (нет транзакций — «банк» был бы голым P&L) и когда ставка больше банка (не внесён депозит — вышло бы +250%). И ДО того, как в учёт впервые вошли деньги: до дня первого депозита и по день первой сверки включительно `balance` — это голый P&L, и история, импортированная за депозитом «сегодня», показывала «−80% банка» за проигрыш в 800 ₽. Это же правило теперь у `calcPlanCompliance` (десктоп): ставки до первого депозита не судятся против банка из собственной прибыли. Выкуп — по факту, через `betPnl`. Карточка читает свой процент СЕЛЕКТОРОМ стора через `bankSharesFor` (кэш на запись), а не пропом через `renderItem`: иначе каждая запись перерисовывала бы все видимые карточки. Под 1% — два знака (`+0.04%`, не `+0.0%`). Всё в `core/__tests__/bankShare.test.ts` и `__tests__/bankShares.test.ts`.
- **Для «читаемости результата за период» — `calcPnlBuckets`**, а не накопительная линия: на кумулятиве выигрышный день идёт вниз, если предыдущий проиграл больше, и это читается как баг.
- **В инсайтах «Лучший/Худший» — это РАНГ, а цвет — знак P&L**. Если все турниры в плюсе, «худший» всё равно красится зелёным: красная цифра на прибыли — вранье о единственном, что там важно.
- **Список лет строится из данных + текущий год** (`calcBetYears`): переключатель сам обзаводится новым годом, когда календарь его отдаёт — ничего релизить и настраивать не нужно.
- **Разбивка по годам живёт на ВСЕЙ истории**, а не на отфильтрованной периодом: пересечение «7 дней» с «2025 год» оставит пустой экран без видимой причины.
- **`calcByTournament(bets, { includeUntagged })`** добавляет группу ставок без турнира под пустым ключом. Для разбивки по годам это обязательно — иначе части перестают складываться в целое.
- **`calcByTournament`/`calcByTeam` отдают `discipline`** — доминирующую СРЕДИ esports-ставок группы (не среди всех): ставка, переведённая с киберспорта на футбол, сохраняет старую дисциплину, потому что форма опускает ключ, а `updateBet` мержит. «Киберспорт» — не ответ: CS2 и Dota это разные игры с разным преимуществом.
- **Фильтр списка ставок** — `BetsFilter { date?, tournament?, team?, from?, year?, noTournament? }`. Турнир сравнивай по `.trim()` с обеих сторон (группировка тримит), команду — через `betBacksTeam()` (то же правило, что у `calcByTeam`), иначе количество в списке не сойдётся с числом на плитке инсайтов.
- **Android «назад»** обрабатывается в `DrawerNavigator` (`BackHandler`): drawer → фильтр → Ставки → выход. Новый уровень навигации добавляй туда же.
- **Подписка на стор — ТОЛЬКО с селектором**: `useBetsStore((s) => s.bets)`, никогда `const { bets } = useBetsStore()`. Без селектора это подписка на весь объект состояния, который zustand заменяет при каждой записи, — любое изменение перерисовывает подписчика. Так карточка ставки (по одной на видимую строку) и навигатор (рендерит активный экран) перерисовывались на каждую запись, а экран заодно пересчитывал статистику. Действия стора стабильны по ссылке, их тоже берут селектором.
- **У бара и заголовка строки — ОДНА величина.** Общий `SliceRow` рисует бар от |P&L|, а крупным числом справа пишет ROI, и на реальных данных они спорят вслух: хоккей (+71.5%, 25 108 ₽) и киберспорт (−3.6%, −25 019 ₽) дают бары одной длины — глаз читает «эти двое равны», пока число говорит о разнице в двадцать раз. В `SportBreakdown` (Аналитика) бар и заголовок — это деньги, ROI ушёл в подпись, а бар расходится от НУЛЕВОЙ ОСИ, поэтому знак несёт форма, а не только цвет. Деньги наверху не случайно: ROI на 12 ставках — это дисперсия, а рубли — то, что произошло; доля оборота стоит рядом, потому что 90% WR на 12 ставках и на 206 — разные утверждения.
- **Тяжёлые `calc*` — в `useMemo`**, и проверять по пути рендера, а не грепом: полный `calcDashboard` может стоять строкой ниже уже обёрнутого вызова, а `isInTilt` — пересчитываться на каждое нажатие в поиске.
- **Значение контекста мемоизируй** (`DrawerContext`): контекст обходит `React.memo`, и свежий объект в `value` перерисовывает всех потребителей на каждый рендер провайдера.
- **`AppText` кэширует разрешение начертания** (`fontCache` в `theme/typography`): каждый `Text` спрашивает его на каждом рендере, и это единственная стоимость, растущая ровно с размером дерева.
- **У длинных списков ограничивай `windowSize`** (9): дефолт RN — 21 экран контента, при 229 ставках это ~110 живых карточек, у каждой свой `PanResponder`. Остальные пропсы батчинга не трогай: `maxToRenderPerBatch` ниже дефолтных 10 только добавляет пустоты на броске, а 50 мс — и так дефолт.
- **`calcLuck` — точка отсчёта НОЛЬ, а не «сколько заработал»**: ставка по цене букмекера имеет нулевое матожидание по построению (`p = 1/odds`), поэтому вопрос не «в плюсе ли я», а «на сколько сигм результат отошёл от нуля». Дисперсия одной ставки — `p(1−p)(stake × odds)²`. Фрибеты, возвраты и выкупы в выборку не входят: модель описывает бинарный исход своими деньгами.
- **`calcPlanCompliance` меряет ставку от банка НА НАЧАЛО дня** (`balance − pnl + withdrawals − adjustments`): пополнения того дня уже учтены, результаты — ещё нет, потому что на момент ставки их не было. Не считай долю от текущего банка — задним числом выигрышный день занизит все доли того же дня.
- **Банк для плана строится по ВСЕЙ истории, судится — срез**: `calcPlanCompliance(allBets, txs, limit, { evaluate: filtered })`. Если восстановить банк из отфильтрованных по периоду ставок, весь P&L до окна пропадёт и появятся выдуманные нарушения (на реальных данных — 10% вместо 7.9%).
- **Действия над ставкой добавляй в `useBetActions`, а не в экран** — колесо показывают два экрана, и позиции секторов должны совпадать, иначе теряется мышечная память.
- **Состояние inline-выкупа держит родитель** (`useBetActions.cashoutFor`), а не карточка: так «две открытые карточки» физически непредставимы. Карточка с открытым полем игнорирует тап по телу, поэтому забытая открытая карточка читается как зависшая.
- **Поле выкупа НЕ привязано к статусу** — выигранную ставку тоже можно перевести в выкуп. По статусу гейтятся только быстрые чипы W/L/R/C.
- **`Alert.alert` после закрытия `Modal` откладывай на кадр** (`requestAnimationFrame`): алерт, показанный от размонтируемого контроллера, может уехать вместе с ним, и подтверждение удаления молча не покажется.
- **`duplicateOf` ≠ `betId`**: `AddBet` с `duplicateOf` заполняет форму из ставки, но сохраняет НОВУЮ — статус сбрасывается в `pending`, дата/время на текущие, `cashoutAmount`/`closingOdds` очищаются.
- **`Text` на мобилке импортируй как `import { AppText as Text } from '.../components/AppText'`**, не из `react-native`. Обёртка подставляет DM Sans и выбирает НАЧЕРТАНИЕ по `fontWeight` (кастомное семейство на Android — одно начертание, `fontWeight: '700'` рядом с `DMSans_400Regular` отрисуется регулярным), после чего снимает `fontWeight`, иначе Android поджирняет уже жирное. React 19 удалил `defaultProps` у функциональных компонентов, поэтому глобального дефолта нет и быть не может. `TextInput` как ТИП рефа по-прежнему берётся из `react-native` (`import type`). **Вложенный `<Text>` обязан задавать свой `fontWeight`**: обёртка пишет разрешённое семейство на КАЖДЫЙ `Text`, поэтому наследование стиля от родителя до вложенного больше не доходит — вложенный элемент с одним лишь `color` отрисуется регулярным рядом с жирным родителем.
- **Деньги, коэффициенты и проценты — со спредом `numeric`** из `theme/typography`: DM Mono, где ширина цифры одинакова по построению. В пропорциональном начертании «1» уже «8», и колонка сумм не выстраивается. `AppText` дополнительно ставит `fontVariant: ['tabular-nums']` по умолчанию. На десктопе то же делает `font-variant-numeric` на `body` в `index.html`.
- **Размеры — только токенами**: `SIZE` (текст: `micro 10 / caption 12 / body 14 / lead 16 / title 20 / hero 26 / display 34`) и `GLYPH` (эмодзи и знаки) из `theme/typography`; `RADIUS`, `SPACE`, `TOUCH`, `hitSlopFor()` из `theme/layout`. Числовой литерал в `fontSize`/`borderRadius` и отступ ≥ 4 мимо сетки 4 px **роняют тест** `__tests__/designTokens.test.ts` — конфига eslint в проекте нет, а jest гоняется в CI. Отступы 1–3 px разрешены: это оптические подгонки (`marginTop: 2` под значением), а не структура. Эмодзи берёт `GLYPH`, а не `SIZE`: смешение этих осей и расплодило 20 размеров.
- **Карточка — `cardSurface`** из `components/Card` (фон, радиус, рамка, тень) или целиком `<Card>`, если нужна шапка с рейлом. Тон накладывается ПОВЕРХ: `{ ...cardSurface, ...toneSurface('profit') }`. Не собирай оболочку руками — так уже появилось четыре радиуса у одного объекта.
- **Статус на карточке ставки — кусок КОНТУРА, а не полоса** (`edge` в `BetCard`): цветная линия 2 px огибает правые углы и уходит по верхнему и нижнему краю на `EDGE_REACH` (72), положена поверх рамки карточки (`top/right/bottom: -1`) с тем же `RADIUS.lg` — на этом отрезке она и есть рамка. Сплошная полоса во всю высоту у карточек, идущих одна под другой, складывалась в одну цветную ленту вниз по экрану, и глаз переставал видеть, где кончается карточка (замечание с телефона). Радиус не пиши числом — он идёт от `RADIUS.lg`.
- **Зона нажатия ≥ 44 dp**: если элемент может вырасти — `minHeight: TOUCH`; если размер намеренный (квадратные степперы, чипы W/L/R/C) — `hitSlopFor(размер)`, он добирает ровно до 44. `justifyContent: 'center'` добавляй только НЕ-строчным контейнерам: у `flexDirection: 'row'` это горизонтальное распределение.
- **Шапка**: экран из drawer — `<ScreenHeader>` (крупный заголовок, гамбургер), запушенный экран — нативная шапка стека с `NAV_TITLE`. Оба начертания идут из одного места в `ScreenHeader.tsx`. `ScreenHeader` держи СНАРУЖИ `ScrollView` — уехавший вверх гамбургер забирает с собой единственный тап в меню.
- **Анимация на нативном драйвере, под которой лежат кнопки, обязана ЗАКАНЧИВАТЬСЯ, когда заканчивается движение.** Пока она идёт, React держит старую раскладку (до анимации), а `Pressability` меряет кнопку именно по ней: при первом микросдвиге пальца палец «вне кнопки» — нажатие отменяется. Боковое меню въезжало пружиной, которая выглядела законченной за ~250 мс и дорабатывала ещё ~700 мс, — после свайпа меню было мёртвым почти секунду. Теперь `Animated.timing` 240 мс с `Easing.out(cubic)`; пружину в `DrawerNavigator` запрещает `__tests__/drawerMotion.test.ts`. Пружина допустима там, где под анимацией нет кнопок, или где хвост незаметен (масштаб 0.86→1 у колеса).
- **Обучение при первом запуске — тур по экрану ставок** (`components/tour/`): затемнение с вырезом над элементом, стрелка от карточки с текстом к нему, «Пропустить» / «Далее» на каждом шаге. Элемент шаг находит по id: экран вешает `ref={tourTarget('summary')}` (меню — через `menuTourTarget` у `ScreenHeader`), оверлей меряет его `measureInWindow` за вычетом собственного смещения. Нет элемента на экране — шаг пропускается, а не показывает стрелку в пустоту; тест сверяет, что каждый `target` из `TOUR_STEPS` где-то зарегистрирован. Где карточка и куда идёт стрелка — чистая арифметика `geometry.ts` под тестом: карточка ниже элемента, если влезает, иначе выше, и НИКОГДА не поверх него. Запуск: `markTourPending()` в конце онбординга (флаг ещё и в памяти — экран монтируется раньше, чем запись доходит до AsyncStorage); флаг живёт до «Пропустить»/конца, поэтому убитое посреди приложение покажет тур снова. Повтор — «Как пользоваться» в Настройках; навигатор сам переводит на экран ставок и закрывает шторку, экран ставок прокручивается наверх и раскрывает панель. Оверлей забирает все касания, Android «назад» его закрывает. Стрелка и обводка — фирменный бирюзовый на затемнении в любой теме, карточка — тематическая. Шаг про Pro — только пока идёт пробный период, с датой окончания (`{{date}}`), а не «7 дней»: при повторе на шестой день «7 дней» было бы враньём. **Затемнение между шагами НЕ гаснет** — плавно меняются только карточка и стрелка (сброс прозрачности в `useLayoutEffect`, до отрисовки); раньше на каждом «Далее» экран на кадр показывался без затемнения. Пока карточка невидима, она `pointerEvents: 'none'`: на Android невидимое принимает касания, и быстрый двойной тап пропускал шаг. Высота карточки меряется по НЕВИДИМОЙ копии без ограничения (`styles.measure`, скрыта от диктора), потому что видимая может быть урезана: если карточка не влезает ни сверху, ни снизу (маленький экран, крупный шрифт), она встаёт на сторону, где места больше, стрелка укорачивается до `MIN_GAP`, а текст прокручивается — но элемент не перекрывается никогда. Старая подсказка-баннер про колесо гасится, только когда тур ДОШЁЛ до шага про карточку: «Пропустить» на первом шаге иначе оставлял колесо необъяснённым.
- **Чек-лист перед ставкой по умолчанию ВЫКЛЮЧЕН** (`defaultSettings.disableChecklist: true`): новый пользователь первые 7 дней — Pro, и пять вопросов перед самой первой ставкой были первым, что он видел. Сохранённые настройки не трогаются — у кого чек-лист включён, у того и остаётся; у настроек, сохранённых ДО появления ключа, отсутствие ключа значило «включён», поэтому `load()` подставляет `false`, а не новый дефолт (тест в `betsStore.test.ts`).
- **Разрешение на уведомления спрашивается один раз, в контексте** — после сохранения первой ставки без результата (`utils/reminderPermission.ts`). Раньше его спрашивала только строка в Настройках, и напоминания о результате (включены по умолчанию, обещаны туром) у нового пользователя молча не приходили: на iOS и на Android 13+ это разрешение времени выполнения. После «да» — перевыпуск напоминаний (ставка, только что сохранённая, планировала своё ДО разрешения) и ежедневное напоминание.
- **`accessibilityState={{ disabled }}` ВЫКЛЮЧАЕТ кнопку**, а не только сообщает диктору: в RN 0.85 `TouchableOpacity`/`Pressable` читают его как `disabled` и не вызывают `onPress`. Кружки «скоро» в выборе темы так стали мёртвыми, и объясняющий алерт не показывался. Если кнопка должна нажиматься, но вести не туда, куда обычно, — `accessibilityHint`, не `disabled`. Страж — `__tests__/pickerGuards.test.ts`.
- **Шит выбора (`FilterPicker`) сначала убирает клавиатуру** (`Keyboard.dismiss()` в `open_`): на iOS прозрачный `Modal` открывается ПОД клавиатурой, поднятой полем суммы, и нижние варианты списка становились недостижимы. То же правило, что у `openDrawer()`.
- **`keyboardShouldPersistTaps="handled"` — на КАЖДОМ `ScrollView`/`FlatList`/`SectionList`**, а не только там, где поле ввода внутри списка. Дефолт RN — `"never"`: при поднятой клавиатуре тап внутри прокручиваемого тратится на её закрытие и до кнопки не доходит, пользователь видит мёртвый первый тап. Клавиатуру могло поднять на ДРУГОМ экране: шторка меню — свой `ScrollView`, и с сфокусированным поиском ставок первый тап по любому пункту не срабатывал. Правило исполняемое — `__tests__/scrollTaps.test.ts`. Плюс `openDrawer()` делает `Keyboard.dismiss()`: клавиатура под шторкой на всю высоту бессмысленна и сама по себе.

## Правила работы (для Claude)

Это не стиль, а то, на чём уже ошибались. Каждое правило — из реального случая.

- **Отметка «сделано» в документации — не доказательство. Проверяй код.** В ROADMAP годами стояло «Easter egg `handleDevTap()` защищён `if (!__DEV__) return`», а проверки не было ни в одном коммите — в релизе 7 тапов раздавали Pro бесплатно. Прежде чем опираться на «уже исправлено», найди это место в коде (`git log -S`, grep). Нашёл расхождение — исправь И код, И запись.
- **То, что экран ПОКАЗЫВАЕТ, и то, что приложение ДЕЛАЕТ, берутся из одной переменной.** Строка напоминания у Free писала «20:00», а планировался сохранённый час бывшего Pro — 09:00. Если значение выводится на экран и где-то применяется, вычисли его один раз и передай в оба места.
- **«Не получилось» и «не дозвонились» — разные ответы.** `restorePurchases()` возвращал `false` и при «подписки нет», и при ошибке сети, и офлайн-пользователь, заплативший за Pro, читал «ничего не найдено». Сервисная функция, которая может не достучаться, возвращает `null` (контракт как у `syncEntitlement`), вызывающий различает три исхода.
- **Проверяй предположение о платформе, а не наличие API.** `typeof Intl.PluralRules === 'function'` ничего не говорит о данных для `be`/`kk`: урезанный ICU молча отдаёт английский. Спрашивай то, что тебе нужно на самом деле (`nativeCoversOurLanguages`).
- **Node ≠ Hermes.** У Node полный ICU, поэтому jest не увидит того, чего нет на телефоне (`Intl.PluralRules`, локали). Если поведение зависит от движка — сымитируй его в тесте (`delete Intl.PluralRules`) и проверь по настоящему эталону (ICU в Node), а не по своим ожиданиям.
- **Правило в CLAUDE.md без теста не исполняется** — в том числе мной: «добавляй ключ во все 4 файла» было записано, и экран фильтров (#61) всё равно ушёл с захардкоженным русским. Новое правило по возможности оформляй тестом (как `designTokens`, `scrollTaps`, `i18n`).
- **Перед мержем в `main`:** `tsc` в mobile И desktop, jest mobile, vitest core, тесты desktop, `expo export` (ловит то, чего не видит `tsc`: импорт, который не резолвится в бандле). Изменение в `packages/core` проверяй на ОБОИХ приложениях.
- **Что не проверено, называй прямо.** Устройства здесь нет: визуал, жесты, поведение Hermes — только типы, тесты и сборка. Пиши это в отчёте, а не подразумевай.
- **«Это баг платформы» — проверь в исходнике зависимости, прежде чем чинить.** Чуть не «исправил» чтение `process.env['EXPO_PUBLIC_…']` по всему приложению: по памяти Expo подставляет только запись через точку, а плагин `babel-preset-expo/build/plugins/inline-env-vars.js` понимает и строковый ключ. Так же проверено, что у абсолютного элемента в Yoga (`ReactCommon/yoga/.../AbsoluteLayout.cpp`) отступы считаются от внутреннего края рамки, — на этом держится контур статуса карточки. Исходник в `node_modules` — ответ; память и «так обычно» — гипотеза.
- **Деньги — отдельное независимое ревью до мержа.** Первый вариант оплаты прошёл все тесты, а ревьюер-агент нашёл два способа потерять ОПЛАЧЕННУЮ покупку (второй счёт затирал первый; сервер забывал счёт через 14 дней) и путь к Pro за тестовый платёж. Тесты проверяют то, что придумал автор; ревью ищет то, чего он не придумал. Каждую находку ревью — тестом (`purchase.test.ts` появился так).
- **Смена дефолта не трогает сохранённое.** `defaultSettings` действует на новые установки; у существующих пользователей в хранилище лежит ВСЁ, включая старый дефолт, и «выбрал сам» от «досталось по умолчанию» не отличить. Перезапись означала бы отменить чей-то сознательный выбор (так сделан чек-лист: новым выключен, у остальных как было).
- **То, что обещают пейвол, лендинг и карточка магазина, — тоже код: сверяй с гейтами.** Пейвол перечислял «Экспорт CSV» среди того, за что платят, а экспорт бесплатный; лендинг обещал OTA-обновления, раздел «Партнёры» с бонусами и импорт Excel на телефоне — ничего из этого нет. За такое отвечают перед покупателем, а Робокасса и модерация RuStore проверяют совпадение сайта с продуктом. Перед тем как написать «в Pro есть X» — найди `ProGate`/`isPro` у X.
- **Секреты и серверная часть — не в публичном репозитории.** Бот поддержки, сервер лицензий, их адреса и ключи — у автора локально, в приложение приходят переменными окружения (`EXPO_PUBLIC_*` в EAS/`.env.local`). Ключи генерирует сам автор (`keygen.html` в браузере), не я: закрытый ключ не должен проходить через эту сессию.

## Цветовая система и темы

**Темы (мобилка): Тёмная / Светлая / Оливковая / Тёмно-синяя.** Устройство, которое нельзя ломать:
- **Палитры — данные** в `theme/palettes.ts` (`PALETTES[id]`, одинаковые ключи, 6-значный hex, `*Dim` — 8-значный). Новый цвет = ключ во ВСЕХ палитрах; тест сверяет ключи и формат и гоняет правила контраста по каждой теме (`__tests__/theme.test.ts`): текст на всех поверхностях ≥ 4.5, сигнальные цвета (won/lost/pending/refund/accent/purpleText/gold/violet/raspberry) как текст на карточке ≥ 4.5, белый на `purple` ≥ 4.4 (фирменный тёмный — 4.41), `onAccent`/`onGold` на своих заливках ≥ 4.5, `onLost` на `lost` ≥ 4.5 (у тёмной — фирменные 3.59), маркер `deposit` ≥ 3 на карточке и плитке и не совпадает с другими сериями графика.
- **`colors` — ЖИВОЙ объект**: `applyTheme(id)` (theme/colors.ts) меняет его значения на месте. Компонент, читающий `colors.x` ПРИ ОТРИСОВКЕ, получает текущую тему — поэтому 900 мест не трогали.
- **Ничего не читает палитру при загрузке модуля.** Таблица стилей уровня модуля — ТОЛЬКО `themedStyles(() => ({...}))` (theme/themed.ts: ленивый прокси, пересобирается при смене темы); `StyleSheet.create` на верхнем уровне запрещён. Общие объекты с цветом (`cardSurface`, `tileStyle`, `HEADER_TITLE`, `NAV_TITLE`, `typography`, `STATUS_COLORS`, `TONE_ACCENT`, `SERIES`, `inputStyle`) — на ГЕТТЕРАХ: спред `{...shared}` в модуле копирует значение один раз. Геттер работает ТОЛЬКО потому, что смена темы перемонтирует дерево: значение снимается заново при следующем рендере, а не по подписке. Нарушение находит статический страж `__tests__/themeLive.test.ts` (TypeScript AST) с указанием файла и строки — он сканирует и `App.tsx`, ловит IIFE (`(() => colors.bg)()`) и вызов `toneSurface(...)` на уровне модуля (так центр доната в Аналитике застывал в тёмной теме — чёрный круг на белой карточке), а отдельный тест проверяет, что сам страж ловит то, что должен. Новый помощник, отдающий цвет темы, — в его `PALETTE_NAMES`.
- **`isThemeId` — только собственные ключи** (`hasOwnProperty`): `'toString' in PALETTES` — правда, и тема стала бы `undefined`. Бэкап тему НЕ везёт: восстановление возвращает ставки, банк, дневник и команды, настройки остаются как на устройстве.
- **Переключение = перемонтаж.** Палитра применяется из подписки на стор, зарегистрированной в `App.tsx` на уровне модуля (раньше любого компонента — до ре-рендера); дерево под `key={theme}` монтируется заново, поэтому замороженные и мемоизированные экраны тоже перерисуются. Стек сохраняется (`initialState`), экран меню — `lastScreen` в DrawerNavigator.
- **Текст на цветной заливке — токен, не литерал**: `colors.onAccent` (галочка на зелёном), `colors.onGold` («Перейти на Pro»), `colors.onLost` (свайп «Удалить», крестик колеса — белый на мягком красном оливковой и тёмно-синей давал 2.5). `'#fff'` допустим только на `purple` — это правило палитры, его держит тест. У ВЫКЛЮЧЕННОЙ кнопки заливка `bgElevated`, а не `purple`, — её подпись `textMuted` (степперы и «+» букмекера в Настройках были белым по белому на светлой).
- **`purple` — заливка, `purpleText` — текст и значки** (спиннеры, `RefreshControl`, кольцо выбранной темы, иконки). У оливковой и тёмно-синей основной цвет — приглушённая олива, она исчезает как тонкая линия на карточке. Маркер депозита на графиках — свой ключ `deposit`: `purpleText` у тёмно-синей совпадает с янтарной линией P&L.
- **Подложка статуса — `signalTint(цвет, сила)`, подпись на ней — `signalInk(цвет)`**, не `colors.won + '18'`. Бейдж статуса, чипы W/L/R/C, квадратики формы на дашборде. Сила задана для тёмной темы (бейдж 0.133, чип 0.094, рамка 0.333) и умножается на `THEME_META[тема].tint`: у оливковой и тёмно-синей 2.2. Подложка 9–13% хороша на почти чёрной карточке, а на коричневой и синей средней светлоты все статусы становились одной мутью — W, L, R и C читались одним серым рядом, «Поражение» почти не отделялось от карточки (жалоба с реального телефона). Более плотная подложка того же оттенка съедает контраст подписи, поэтому `signalInk` сдвигает её к `textPrimary` на `THEME_META.ink` (0.45; у светлой 0.15 — к тёмному, это заодно подняло «Ожидание» до AA). Тёмная тема — `tint: 1, ink: 0`, байт в байт как была. Тест: каждая подпись на своей подложке ≥ 4.5 (тёмный красный — исторические 4.43), подложка у тем средней светлоты отстоит от карточки ≥ 1.5.
- **Сигнальные цвета оливковой и тёмно-синей — насыщенные** (насыщенность 60–100% вместо 40–50%): пастельные победа/поражение/ожидание проходили контраст по светлоте, но сливались с бежевым текстом и коричневым фоном по оттенку. Светлота — не единственная ось: «читается» и «выделяется» — разные проверки.
- **Поверх затемнения — фиксированные светлые цвета**, не тема: заголовок колеса действий лежит на чёрной подложке, и тёмный текст светлой темы там пропадал (`PALETTES.dark.textPrimary`).
- **Логотип — `tintColor: colors.textPrimary`**: это белый знак на прозрачном, на светлой карточке без тинта он исчезал.
- **Заставка — бренд, не тема**: `AnimatedSplash` и подложка сплэша в `App.tsx` всегда в `PALETTES.dark` — они продолжают нативный сплэш, светлая заставка после тёмного нативного мигала бы.
- **Тени зависят от темы**: у карточки 0.35 на тёмных и 0.08 на светлой; тень боковой шторки — только когда она открыта (спрятанная за краем, она давала серую полосу у левого края на светлом фоне).
- **`react-navigation` получает тему** (`navigationTheme()` в App.tsx) — без неё фон стека в переходах был светло-серым DefaultTheme.

## Оплата и Pro (мобилка)

Устройство, которое нельзя ломать. Код в репозитории — приложение; **сервер лицензий (Cloudflare Worker) в репозитории НЕ живёт**, как и бот поддержки: он у автора локально, его адрес и публичный ключ приходят из переменных окружения.

- **Способ оплаты выбирается сборкой**: `EXPO_PUBLIC_BILLING` (`services/billing.ts`) — `robokassa` (по умолчанию, RuStore) или `revenuecat` (Google Play / App Store, позже). Задан явно в КАЖДОМ профиле `eas.json`: `rustore`/`preview` — `robokassa`, `production` (Google Play) — `revenuecat`; сборка под Play с внешней оплатой нарушила бы правила Play. RevenueCat инициализируется и спрашивается ТОЛЬКО в сборке `revenuecat`: в сборке для RuStore его «нет» отняло бы Pro, оставшийся от старой сборки. RuStore Pay закрыт для самозанятых с 1 февраля 2026, а оплата через Google Play в России не работает — поэтому Робокасса. Продавец — ИП на НПД: чеки через «Мой налог» («Робочеки СМЗ»). Реквизиты ИП и оферта должны быть на лендинге (`gh-pages`: подвал, `offer.html`) — оферта свёрстана, ждёт ФИО, ИНН, ОГРНИП и город; публиковать с заглушками нельзя (Робокасса отклоняет).
- **Откуда установлена сборка — `EXPO_PUBLIC_DISTRIBUTION`** (`utils/storeLinks.distribution()`), тоже в КАЖДОМ профиле: `rustore`, `store` (Google Play / App Store — `production`), всё прочее — `direct` (APK руками: GitHub, тестеры — `preview`, `development`). От неё зависят «Оценить» (RuStore → веб-страница `https://apps.rustore.ru/app/<пакет>`: deeplink `rustore://` на карточку приложения не задокументирован, а RuStore принимает ЛЮБУЮ `rustore://`-ссылку — неверный путь открыл бы его главную, и запасной вариант не сработал бы; `direct` — строки нет, и на iOS тоже) и проверка обновлений через GitHub (ТОЛЬКО у `direct`, и только по релизам, где есть APK, — `utils/appUpdates`: большинство тегов в репозитории десктопные, а `/releases/latest` отдаёт последний по времени). Раньше сборка для RuStore слала оценивать в Google Play, где приложения нет, а «Доступна X» сравнивала с последним тегом GitHub — в том числе десктопным — и обещала версию, которой в RuStore ещё нет. Пару «магазин ↔ оплата» в `eas.json` держит `storeLinks.test.ts`.
- **Ни одного пароля Робокассы в приложении.** Паролем №1 подписывается ссылка на оплату и проверяется SuccessURL: достанут из APK — сделают ссылку на 1 ₽ и подделают «оплачено». Подтверждение оплаты приходит ТОЛЬКО на сервер (ResultURL, Пароль №2). Приложение спрашивает сервер «оплачено ли» по счёту + одноразовому `nonce`, который знает только телефон, открывший счёт.
- **Лицензия** — `SL1.<base64url(JSON)>.<base64url(Ed25519)>` (`utils/license.ts`), подпись по ASCII сегмента полезной нагрузки. Сервер подписывает закрытым ключом, приложение проверяет публичным (`EXPO_PUBLIC_LICENSE_PUBKEY`) через `tweetnacl` — чистый JS, работает на Hermes без нативного модуля (его `require('crypto')` Metro заменяет пустым модулем — для проверки подписи генератор случайных чисел не нужен). `verifyLicense` никогда не бросает: мусор вместо кода = `null`. **Проверяется ОДИН раз — на входе** (`applyLicense`: код восстановления, бэкап, ответ сервера — единственный писатель `settings.license`); дальше лицензия — обычные данные (`hasLicense`). Проверка на каждом запуске стоила ~100 мс JS (Ed25519 на чистом JS, Hermes без JIT) и не защищала ни от чего: то же хранилище держит сам `isPro`. Вставленный текст разбирается `extractLicense`: люди хранят код в Telegram, и сообщение «Код восстановления …: SL1…» с переносом строки должно подходить целиком. Совместимость с WebCrypto-подписью сервера проверяет `license.test.ts` (подписывает Node `crypto`, не tweetnacl). Последний символ base64 у 64-байтной подписи несёт два пустых бита — менять в тестах надо середину.
- **Безопасность — бэклог в ROADMAP** («🔐 Безопасность»): обход Pro через сохранённый флаг и часы, тестовые лицензии, проверка бэкапа — ДО релиза в RuStore. Свой Pro на время разработки — `EXPO_PUBLIC_OWNER_PRO=true` в `apps/mobile/.env.local` или в EAS-переменных окружения `preview`, НИКОГДА в `eas.json` (держит `storeLinks.test.ts`) и не в окружении `production` — его берёт и профиль `rustore`. Окружение EAS названо в профиле явно (`preview` → `preview`, `development` → `development`, `rustore` → `production`), тест это держит: переменная владельца из `preview` не может попасть в сборку для магазина. Пока переменной нет, Pro разработчика держится на сохранённом флаге (`resolvePro` → `previous`) — до исправления из бэклога и только при установке ПОВЕРХ (та же подпись, без удаления приложения).
- **Возврат в первые 7 дней обязателен** — ст. 48 Единых правил защиты прав потребителей (Декрет ВГС № 6 от 06.12.2024): цифровой продукт надлежащего качества возвращается в течение 7 дней, даже активированный. Оферта это отменить не может. Защита от «купил — попользовался — вернул» — ОТЗЫВ кода после возврата (в бэклоге, «⚖️ Оплата»), а не формулировки. Разбор и черновик оферты — `docs/legal/`.
- **Pro решает `resolvePro`, а не флаг**: владелец или валидная лицензия → Pro; магазин сказал «да» → Pro; идёт пробный период → Pro; пробный кончился → нет; магазин сказал «нет» → нет; иначе — сохранённый флаг (Pro из старой сборки не отнимаем). `settings.isPro` — кэш, пересчитывается в `load()`, после ответа RevenueCat (`refreshPro(entitled)`) и при каждом возврате в приложение. Раньше ответ RevenueCat «нет» писался прямо в `isPro` и выключил бы и пробный период, и лицензию.
- **Пробный период 7 дней** — локальный: `startTrial()` в конце онбординга, дата в `proExpiresAt`. Не дважды и не поверх лицензии. Переустановка его сбрасывает — для старта принято. Покупка в магазине стирает дату пробного, иначе офлайн-запуск после него прочитал бы «кончился».
- **Оплата завершается в браузере**, поэтому незакрытый счёт лежит в AsyncStorage (`@sharklog/pending_payment`), а `resumePendingPayment()` (`services/purchase.ts`, один запрос на всех одновременных) спрашивает сервер при запуске, при возврате в приложение и по кнопке «Проверить оплату». **Забытый счёт = потерянная оплаченная покупка** (без его `nonce` лицензию не забрать), поэтому: `createPayment()` НЕ выставляет новый счёт поверх ждущего, а возвращает его (пейволов живо несколько — экраны в шторке не размонтируются — и покупка с устаревшего затирала только что оплаченный счёт; двойной тап делал то же); отмена ожидания — только через подтверждение; неоплаченный счёт забывается через 30 дней; ответ сервера `unknown` (не этого телефона счёт) — повод забыть сразу, иначе пейвол навсегда «ждёт». «Pro включён» говорит тот, кто первым взял `takePaidNotice()`, и через кадр — алерт из закрывающегося шита на iOS пропадает.
- **Сервер до оплаты счёт НЕ хранит**: всё о нём едет в ссылке в подписанных `Shp_amt` (цена при выставлении) и `Shp_nh` (хеш nonce), Робокасса возвращает их в уведомлении под Паролем №2. Одна запись в KV на покупку: спам не исчерпает лимит записей, счёт не «протухает», смена цены не ломает выставленные. Тестовая оплата (`IsTest=1`) засчитывается, только пока сервер в тестовом режиме.
- **Цена — с сервера** (`/offer`): число на кнопке и число, которое спишет Робокасса, — одно. Нет связи — кнопка не показывается, пишется почему (не «мёртвая кнопка с придуманной ценой», как было у пейвола RevenueCat без продуктов).
- **Код восстановления = лицензия.** Настройки: «Код восстановления» (поделиться) / «Ввести код восстановления» (`RestoreCodeSheet`). Лицензия едет в JSON-бэкапе внутри `settings` и при восстановлении применяется, только если проверка подписи прошла. Потерян код — автор достаёт лицензию по номеру счёта через служебный маршрут сервера (`/admin/license`, токен в заголовке) или командой бота поддержки `/license <счёт>`: ответом на сообщение пользователя код уходит ему на его языке. Бот обращается к серверу лицензий через service binding, а не по адресу: воркер не достучится до другого воркера того же аккаунта на `workers.dev`.
- **`PaywallSheet` закрывается на ПОКУПКУ, а не на Pro**: в пробный период пользователь — Pro и всё равно пришёл купить. Поэтому шит показывает `ProOffer`, а не `ProGate` (тот показал бы содержимое).

## Локализация (i18n)

Поддерживаются 4 языка: **ru** (русский), **en** (English), **kz** (қазақша), **by** (беларуская).

Файлы переводов:
- Desktop: `apps/desktop/src/i18n/locales/{ru,en,kz,by}.json`
- Mobile: `apps/mobile/src/i18n/locales/{ru,en,kz,by}.json`

```typescript
// Desktop — в компонентах
import { useTranslation } from 'react-i18next';
const { t, i18n } = useTranslation();
t('status.won')           // → 'Победа' / 'Won' / 'Жеңді' / 'Выйграў'

// Смена языка (десктоп — через SettingsPage)

// Mobile — через applyLanguage() в SettingsScreen
import i18n from '../i18n';
i18n.changeLanguage(lang);

// Локаль для дат

```

Ключевые пространства имён в JSON-файлах:
`nav`, `status`, `bet`, `dashboard`, `analytics`, `insights`, `bankroll`, `discipline`, `settings`, `common`

Соглашения:
- `formatPercent()` не трогать — уже добавляет `+`; в переводах знак `+` тоже не ставить
- Валюта `₽` захардкожена в `formatMoney()` — не переводить
- Все числовые суммы идут через `formatMoney()`, не вставлять в строки вручную
- При добавлении нового UI-текста — добавлять ключ во все 4 файла сразу. **Теперь это исполняемое правило** (`apps/mobile/src/__tests__/i18n.test.ts`): ключи сверяются между файлами, `{{переменные}}` у ключа одинаковы во всех языках, пустых строк нет.
- **Захардкоженный русский — храповик.** В том же тесте карта `UNTRANSLATED`: файл → сколько строк с кириллицей в нём ещё осталось. Число может только ПАДАТЬ: новый файл обязан быть нулевым, рост числа роняет тест, а переведённую строку тест требует вычесть из карты (иначе ослабший храповик пропустит следующую). Это и есть оставшаяся работа по переводу, файл за файлом. Исключение одно — `i18n/index.ts`: язык называется на самом себе («Қазақша», «Беларуская») и не переводится никогда.
- **Коды языков: в настройках `kz`/`by`, в i18next — `kk`/`be`.** `kz` и `by` — коды СТРАН; они уже лежат в сохранённых настройках на устройствах, поэтому остаются. Но i18next выбирает формы множественного числа через `Intl.PluralRules`, и `Intl.PluralRules('by')` молча резолвится в английский: белорусский получал две формы вместо четырёх, и «21 стаўка» с «5 ставак» печатались одной строкой. Ресурсы зарегистрированы под `kk`/`be`, перевод кода — `toI18nCode()`; язык переключай ТОЛЬКО через `applyLanguage()`, не через `i18n.changeLanguage` напрямую. Ключи в JSON-файлах `kz.json`/`by.json` остаются как есть.
- **Множественное число — суффиксы `_one/_few/_many/_other` (ru, by) и `_one/_other` (en, kz)**, вызов `t(key, { count })`. Тест требует у ключа ровно те формы, что нужны языку. Hermes, скорее всего, не даёт `Intl.PluralRules`, а без него i18next не падает, а тихо берёт заглушку «1 → one, иначе other» — и РУССКИЙ тоже теряет формы. Поэтому `i18n/pluralRules.ts` ставит свой мини-полифил, если движок не дал своего ИЛИ дал без данных для наших языков (урезанный ICU молча резолвит `be`/`kk` в английский — тот же баг другой дорогой; проверяет `nativeCoversOurLanguages`). Тест сверяет полифил с настоящим ICU на 0…1000 и дробях. Ловушки, которые он закрывает: «21 поражения», «11 поражений», «21 день».
- **Счётчики в алертах — форма «Найдено ставок: 12»**, без склонения: она верна при любом числе на всех четырёх языках. Настоящее множественное число — там, где без него фраза читается коряво («после 3 поражений подряд», «5 дней назад»).
- **Хранимый `pick` — ФОРМАТ ДАННЫХ, не текст: `PICK` в core** (`П1`, `П2`, `Ничья`, `Ф1`, `Ф2`, `ТБ`, `ТМ`, `Да`, `Нет`, `Экспресс`). По ним `getPickedTeams` находит сторону ставки (статистика по командам, фильтр), форма разбирает их обратно при редактировании, CSV везёт между устройствами. Переведи их — и у англоязычного пользователя статистика по командам молча опустеет, а смена языка осиротит все сохранённые ставки. Пишутся ВСЕГДА по-русски; ПОКАЗЫВАЮТСЯ через `pickLabel(t, pick)` (`utils/labels`), который меняет только целые токены (`Ф2 (-6.5)` → `H2 (-6.5)`, «Пари НН» не трогает). Формат заморожен тестом `core/__tests__/pickTokens.test.ts` — меняй только вместе с миграцией сохранённых ставок. То же для подписи типа ставки, которую форма записывает в `pick` у типов без уточнения (`BET_TYPES[type]`).
- **Заметки, которые приложение пишет САМО, — тоже формат данных: `TX_NOTE` в core** (`ADJUSTMENT` «Сверка с букмекером», `INITIAL_DEPOSIT` «Начальный депозит»). Они лежат в сохранённых транзакциях и уезжают в бэкап, поэтому пишутся по-русски всегда, а показываются через `txNoteLabel(t, note)` — он переводит только эти две, введённую руками заметку отдаёт как есть. Пустая причина сверки сохраняется как `TX_NOTE.ADJUSTMENT`, а не как переведённая строка: иначе заметка навсегда застынет на языке, на котором её создали. Имя банка по умолчанию (`DEFAULT_BANKROLL_NAME`) хранится и нигде не показывается. Заморожено тем же `pickTokens.test.ts`.
- **Дробное число из поля ввода — `parseFloat(x.replace(',', '.'))`.** Русская, казахская и белорусская `decimal-pad` клавиатура даёт ЗАПЯТУЮ, а `parseFloat('1,85')` молча возвращает `1`: калькулятор Келли при кэфе «1,85» считал по кэфу 1 и предлагал не ставить. Ошибки нет, NaN нет — просто неверный ответ.
- **Подписи из core — только через `utils/labels`** (`sportLabel`, `betTypeLabel`, `strategyLabel`, `disciplineLabel`). `SPORTS`/`BET_TYPES`/`STRATEGIES`/`ESPORTS_DISCIPLINES` хранят РУССКИЕ подписи, и экран, который их индексирует, показывает русский на любом языке — а храповик этого не видит, кириллица-то в core. Так «переведённая» карточка ставки показывала «Киберспорт · Фора». Брать из этих карт КЛЮЧИ (`Object.keys` — для порядка вариантов) можно; читать ПОДПИСИ — нельзя, это ловит второй страж в `i18n.test.ts` (с короткой разрешённой картой и списком ещё не переведённых экранов, который может только сокращаться).
- **Тексты билдера стратегий — из ОТВЕТОВ, а не из сохранённой стратегии.** `buildStrategy` запекает имя, описание, обоснование и принципы в `GeneratedStrategy` на языке момента создания: стратегия, собранная по-русски, оставалась русской после переключения на английский — на экране результата, на плашке дашборда, в строке настроек. Какое предложение достаётся профилю, решает core (`strategyTextIds(answers)`), слова — ключи `strategy.*` на мобилке через `utils/strategyText` (`strategyTexts`, `strategyName`, `strategyQuestions`). Сохранённые строки — только запасной вариант для записи без `answers`; десктоп по-прежнему показывает запечённые ru/en, и вывод `buildStrategy` после рефакторинга побайтно тот же (сверено на всех 116 640 профилях). Читать `STRATEGY_QUESTIONS` или `strategy.name/rationale/...` мимо `utils/strategyText` запрещает страж в `i18n.test.ts`; `strategyText.test.ts` обходит ВСЕ профили и требует каждый ключ во всех четырёх языках — он же поймал, что подпись «Коэффициенты» под ключом `strategy.odds` затирала группу обоснований диапазона.
- **Core, который сам формирует подписи, принимает подписчика.** `calcByDayOfWeek(bets, dayName?)` по умолчанию называет дни по-русски (десктоп не меняется), экран передаёт `(d) => t(\`weekdays.${d}\`)`. Это третий путь русского мимо храповика — наравне с картами подписей: экран чист, а «Понедельник» печатает ядро. Новая функция core, отдающая текст для экрана, делает так же.
- **Месяцы — из ключей `monthsShort.N` / `monthsLong.N`, не из `Intl`**: подписи столбцов шириной в три буквы, а у движка без данных `kk`/`be` формат молча откатится.
- **Не затеняй `t`.** Где имя `t` уже занято (проп `t: TournamentStats`, `const t = calcTimeStats(...)`, `const t = split(...)`), переводчик называется `tr` (`const { t: tr } = useTranslation()`) с комментарием почему. Типы такое не ловят: внутри затенения `t('…')` — вызов не той функции.
- **Неизвестное значение показывай как есть**: `t(\`sports.${v}\`, { defaultValue: String(v) })` — у старой или вручную отредактированной ставки иначе на экране появится сырой ключ `sports.mma`.
- **Голос:** русский на «ты»; казахский и белорусский исторически переведены на «вы» («Pro-ға өтіңіз», «перайдзіце») — новые строки держат тот же голос, что уже есть в файле.
